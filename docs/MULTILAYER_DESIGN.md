# Arbor 多层完整跨片执行设计

日期：2026-10-03。本轮扩展多层拓扑上的完整交易执行，并支持两个以上参与叶子。采用当前用户确定的逐批处理方式：叶子不推测执行，不提前处理后续业务槽；上层收齐所有实际参与叶子的完成证明后直接结束，不再为这些回复发起共识。测试结果以本轮验收报告为准。

## 1. 目标和保留行为

- 每个分片仍有 4 个独立进程，固定 `n=4, f=1`，实际运行 Ed25519 验签与 PBFT 投票。
- 所有编辑配置集中在 `config/`，运行目录、分片目录和日志保持在配置目录之外。
- 任意合法树形拓扑、非连续 ID、不同叶子深度均可选择至少两个不重复叶子参加跨片交易。
- 一笔跨片交易的协调者是其参与叶子的最近公共祖先（NCA）；请求内的交易须具有同一 NCA，并按照参与集合兼容合批。
- 客户端首次只发送目标分片的 `f+1=2` 个副本，保留超时退避重试和两个不同副本一致回复的确认标准。
- 保留请求、交易、PBFT 投票和跨片证书去重，forward 汇总认证票后发送，TCP 长连接、增量去重维护、增量状态摘要、检查点摘要缓存和网络定时阻塞等待。

本轮未实现片内/跨片队列公平轮转、状态重分区、自适应扩缩容、SharPer 对照方案、多线程执行、整片断电恢复、跨片统一读取屏障或超时 abort。

## 2. NCA 直接向参与叶子下发

拓扑用于确定 NCA 和祖先集合，不要求 TCP 沿树逐跳转发。一笔由根 7 协调、访问叶子 1 和 3 的交易，认证订单直接发给叶子 1、3；协调者 5、6 不为这笔祖先交易再做一次业务共识。

```text
             7
         /       \
        5         6
       / \       / \
      1   2     3   4
```

| 参与叶子 | NCA | 业务排序片 | 本地执行片 |
|---|---:|---|---|
| 1、2 | 5 | 5 | 1、2 |
| 3、4 | 6 | 6 | 3、4 |
| 1、3 | 7 | 7 | 1、3 |
| 1、2、3 | 7 | 7 | 1、2、3 |

Prepared 依赖 QC 在所有实际参与叶子之间直接交换；ACK QC 只回到该批次 NCA。各叶只更新自己的正式 KV，协调者不执行叶子程序。

链路延时按照实际通信的源分片和目标分片查询 `network.shard_links`，缺项使用 `default_inter_shard_delay_ms`。例如根 7 直接向叶子 1 发送，应用的是 `7↔1` 延时，不能自动把 `7↔5` 与 `5↔1` 相加。

## 3. 为什么多层需要封闭证书

简单地让叶子按到达顺序处理各个 NCA 的订单会造成环形等待。例如协调者 5 排序访问叶子 1、2 的订单 A，根 7 排序访问叶子 1、3 的订单 B。若叶子 1 先暂存 A、叶子 3 先暂存 B，后续还可能有协调者 6 与根的其他订单构成依赖环。每片单批在途时，消息到达顺序无法保证全局无环。

仅排序已收到的订单也不足以判断“更早的订单不存在”：某祖先可能尚未发出本轮订单。因此每个叶子需要可认证的证据，证明其所有祖先本轮订单已经确定。这就是轮次封闭的作用。

论文第 V-B 节按最小叶子 ID 对已经观察到的顺序分歧进行调整。本实现采用认证轮次和固定协调片顺序，先证明本轮输入完整，再逐批执行；它不进行事后重排或重做。轮次机制是本阶段的保守工程选择，实验及论文协议描述应明确对应这一选择。

## 4. 按需轮次与 PBFT 封闭

当树中有多个协调者时，采用正整数轮次 `cst_round`。没有业务需求时不持续产生空轮次。

1. 有待排序请求的协调者开启下一轮，并由 forward 向其他协调者发送 `CST_ROUND_REQUEST {target, round}`。
2. 每个协调者在本轮最多通过一次 PBFT 封闭：若有适用请求，封闭值包含业务订单；若无请求或受在途业务上限控制，封闭值的 `requests=[]`。
3. 封闭值带本轮编号，以及该协调者所有后代叶子的累计订单流计数 `cst_watermarks`。
4. 协调者 forward 将带完整 PBFT 证书的 `CST_ROUND_CLOSE` 发给其所有后代叶子，包括不参与本轮业务订单的叶子。
5. 叶子收齐自己所有严格祖先在同一轮的封闭证书后，按 `(round, coordinator_id)` 升序处理其中与自己相关的业务订单。

同一个封闭 PBFT 可以同时承载业务排序和封闭声明；空封闭也运行真实 PBFT，因此确实有计算、签名、网络与日志成本。它不代表祖先订单被中间协调者重新共识：中间片只认证自己的订单流本轮已封闭。

只有一个协调者的两层拓扑保留直接 `CST_ORDER` 路径，不需要多协调者轮次控制。两方交易仍为一次协调者 ORDER PBFT 加每个叶子一次 PBFT；`p` 个参与叶子对应正常 `1+p` 次分片 PBFT。多协调者路径还包含其他协调者本轮的封闭 PBFT，不能将它笼统算成只有 `1+p` 次。

## 5. 累计水位与叶子前沿

协调者的封闭值包含：

```json
{
  "requests": [],
  "cst_round": 3,
  "cst_watermarks": {"1": 2, "2": 1, "3": 0, "4": 0}
}
```

其中 key 是字符串形式的后代叶子 ID，value 是该协调者已经排序且实际涉及该叶子的批次数。一批涉及某叶子时计数加 1；多个交易或多个请求合入该批仍只加 1。空封闭不增加计数。有业务订单的值另有 `cst_order_index`，它是该协调者自身业务批次的连续编号；它不等于全树统一顺序。

叶子业务状态中的 `cst_indices[coordinator_id]` 保存自己已经执行完成的该协调者订单流计数。这解决了“协调者连续排序 A、B，但 B 不访问该叶子”时的跳号问题：叶子不必等待本来就不属于自己的业务批次。

叶子提议执行订单时，将所有祖先本轮的封闭证书放入 PBFT 值的 `cst_frontier`。每个备份独立检查：

- 所有证书来自其严格祖先，祖先不重复且集合完整。
- 所有证书绑定同一正整数轮次，并有合法 PBFT 提案、PREPARE 与 COMMIT 证据。
- 每个祖先声明的投影计数与本片已完成计数一致；若该祖先本轮有尚未执行的本片订单，只能比已完成计数大 1。
- 已执行订单的内容摘要必须匹配原证书。
- 本轮相关且尚未执行的祖先订单中，当前候选必须是 coordinator ID 最小者。
- 已执行轮次不能回退；漏掉前序订单时累计投影水位会暴露缺口，后序订单不能跳过。

`cst_frontier` 是已签名 PBFT 值的一部分，不能仅依赖主节点本地声称“已经收齐”。已准备历史提案在视图切换中保留其原认证值，状态追赶仍需要原执行 witness。

## 6. 叶子逐批执行与完成

对实际参与叶子集合 P，一批业务沿用现有同槽协议：

1. 每叶验证 NCA 订单证书和必要的祖先前沿；只有本片当前主节点提出该业务槽。
2. 本片 PBFT 提交后生成临时读快照、逐笔输入和 Fibonacci 结果，向本片 forward 发送 Prepared 票。
3. forward 收齐 3 个不同副本一致签名，得到本片 Prepared QC，片内分享并发给其他实际参与叶子。准备票的 `record_digest` 绑定 `shard、batch_key、order_digest、reads、writes`，不包含订单证书的签名子集；订单证书仍单独完整验证，避免 forward 接替时合法 QC 子集变化把同一结果分成两组。
4. 叶子收齐 P 中所有叶子的 Prepared QC，验证同一 batch key、订单摘要及执行上下文，在原已提交槽内执行并写本片状态。
5. 每叶 forward 收齐本片 3 个一致 ACK 签名，向该批 NCA 发送 ACK QC。
6. NCA 验证并去重，收齐 P 中所有叶子的完成证明后，直接恢复请求结果并向客户端回复。此时不追加 DECISION、FINALIZE 或 DONE 共识。

单个叶子只保留一个 staged 批次；依赖不足时其正式 KV、应用序号和业务摘要均不推进，后续业务槽等待。已有认证订单和证明可以提前缓存，但这不表示叶子流水线执行或推测执行。

## 7. 多参与叶子的确定性合成执行

每笔交易为每个参与叶子声明一个 key 和输入值。设本笔开始时叶子 i 的 key 值为 `old_i`，声明值为 `input_i`，则：

```text
new_i = input_i + sum(old_j for j in P and j != i) + fib
```

先使用本笔开始前所有参与叶子的 working state 计算全部新值，再同时更新各 working map；后续交易读取本批前序交易已更新的值。整数为 `uint64_t`，按模 `2^64` 回绕；各本地 key 的 version 增加 1。

本地状态摘要绑定旧本地状态、按叶子 ID 升序排列的全部远片旧状态、交易及 owner。两个参与叶子的情形保持此前值计算与摘要输入规则。`execution_digest` 依据按叶子 ID 排序的确定性 records，不依赖合法三签子集选择；各叶应得到相同执行上下文摘要，而 `result_digest` 和 KV 可以不同。

例如叶子 1、2、3 的旧值分别为 10、20、30，声明值均为 1，fib 为 1，新值为 52、42、32。每叶均实际计算 Fibonacci；跨片执行完成数在客户端只计一笔，不能把三个叶子的执行计数相加作为系统 TPS。

## 8. 消息、状态与恢复

| 对象 | 用途 |
|---|---|
| `CST_ROUND_REQUEST {target, round}` | 按需要求协调者完成指定轮次封闭 |
| `CST_ROUND_CLOSE {target, certificate}` | 协调者 forward 向后代叶子发送认证封闭 |
| `CST_ROUND_QUERY {target, rounds, leaf, after_index}` | 查询缺失封闭和投影流缺口，每次最多 32 轮 |
| `CST_ROUND_PROOFS {target, certificates}` | 返回认证封闭证书 |
| 协调者 `participant_indices` | 每个后代叶子的累计业务订单流计数 |
| 协调者 `cst_rounds[round]` | 保存封闭槽的 seq、摘要和确定性 value，进入状态摘要与检查点 |
| 叶子 `cst_indices[origin]` | 本片对每个祖先订单流已完成的累计计数 |
| `cst_round` | 协调者最后封闭轮次，或叶子最后执行业务所在轮次 |
| 易失 `roundCertificates` | 完整认证封闭证书缓存，由状态追赶与查询补回 |

当叶子仅收到后序订单时，查询不仅请求当前缓存订单所在的轮次，还通过 `after_index` 补取该祖先最早缺失的相关订单。否则只追问最新轮次会永远填不齐投影缺口。

协调者状态追赶获得 `cst_rounds` 元数据后，若缺完整封闭证书，向本片存活同伴补取；forward 恢复后再下发。完成缓存仍依据原 ORDER 与全部参与叶子的 ACK QC 补回，不为历史完成再次进行业务共识。Prepared/witness 证据仍按原查询路径补取。

落后协调者收到较远的正整数轮次请求时，将当前目标限制在已封闭轮次加 64 以内，先逐轮追赶；不会因为一次请求超出 64 而永久拒绝其真实目标。叶子查询尚未生成的未来封闭时，`CST_ROUND_QUERY` 也会按相同上限推进协调者的 `desiredRound`。后续请求与查询继续推进，使落后的分支最终补齐目标轮次，避免只有快分支持续前进。

PBFT 副本收到合法签名、位于接收水位内的后序 `PREPREPARE` 时，即使该提案因本地状态或祖先前沿尚不能接受，也记录 `catchupTarget = max(catchupTarget, seq - 1)`，表示缺失的前缀。合法后序提交证据同样可提高追赶目标。副本在无进展且达到重试间隔后发送 `SYNC_REQUEST`，事件日志记录 `sync_requested {after, target}`，状态输出暴露 `catchup_target`。追赶触发不依赖必须先发生视图切换；健康副本不因定时器持续广播全量同步。

本轮修复了两处容易造成恢复误判的实现问题：

- 跨片查询的源副本和目标 forward 即使同为 replica 0，也属于不同分片，必须返回封闭证明。现在只抑制真正的同片同副本自发自收，不再仅比较 `sender == me`。
- 视图切换测试的合成 genesis 快照补齐 `cst_round=0`、`cst_indices={}`、`participant_indices={}` 和 `cst_rounds={}`。这些新字段参与认证状态摘要；旧格式测试快照会因摘要不匹配而被正确拒绝，不能把该拒绝误当成正常 prepared 恢复失败。

这些恢复能力依赖活副本和历史证据仍存在。审计日志不是具有 fsync 投票保证的 WAL；同 run 崩溃重启、整片断电和任意阶段故障组合的完整恢复仍未提供。

## 9. 观测与性能统计

节点新增 `cst_round`、`cst_indices`、`rounds_requested`、`round_certificate_count` 和 `catchup_target` 等状态字段；`sync_requested` 是节点事件日志项，而不是状态计数器。叶子只在实际执行业务时推进 `cst_round`，纯空封闭不要求非参与叶子运行一次业务 PBFT。

多层 benchmark 只要求：实际 NCA 排序、完成 count 笔；参与叶子各执行 count 笔；其他分片业务计数为 0。无关协调者的 `applied_batches` 可以由于空封闭增加，但其四副本必须收敛，且不得存在 `rounds_requested > cst_round` 的未封闭轮次。所有队列和网络发送缓存仍须排空。

客户端成功确认必须得到目标 NCA 两个不同副本的一致认证回复，且每个参与叶子已经提供完成 QC。完整跨片的客户端 `ordered_only_transactions` 必须为 0；内部订单记录先处于 ordered 状态不等于提前向客户端报告完成。TPS、平均延时和 p50/p95/p99 均按照客户端唯一执行完成交易统计，延时单位为秒。

多协调者轮次增加空封闭证书广播与 PBFT 成本；层级、参与片数量、分片数量和共享 CPU 均会影响吞吐。不能用此前两层三分片的历史结果宣称本轮多层性能已经达到相同水平。

## 10. 配置、测试与当前限制

`config/three_layer.json` 为 7 分片、28 节点。`config/four_layer.json` 为紧凑非均匀四层树：叶子 1、2 在 5 下，叶子 3、4 在 6 下；5、6 在 7 下；协调者 7 和叶子 8 在根 9 下，共 9 分片、36 节点。

完整测试命令及预期业务计数见 [../TESTING.md](../TESTING.md)，独立性能测试见 [BENCHMARK.md](BENCHMARK.md)。建议先小负载验证兄弟叶子、不同子树叶子、三个参与叶子、跨三个祖先层级的叶子，再提高 count 和 rate。

固定轮次封闭提供顺序完整性，代价是某个必要祖先的空封闭延迟也会阻塞叶子。当前没有独立 forward 投诉机制，也没有跨片 abort；合法心跳下持续扣留证明的 forward、永久失效参与分片、历史证明全部丢失均可能影响进展。本文描述工程实现，不把它等同于论文全部故障模型、扩缩容或状态划分机制已经复现。


本轮实际验收：`make test` 112 项检查通过；两层、三层及四层共 12 轮隔离集群全部完整完成并收敛。测量条件、额外成本和结果见 [MULTILAYER_VALIDATION.md](MULTILAYER_VALIDATION.md)。
