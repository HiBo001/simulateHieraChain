# Arbor 两个低层区块合并提交实验（2026-10-12）

## 实现

配置 `config/three_layer_lower_bundle.json` 在低层优先流式模式下设置 `ancestor_lower_blocks_per_root=2`、`ancestor_leaf_batch_blocks=2`。这次两个协调者区块的真实QC一起进入一次叶子PBFT，原2:1实验每个区块仍各做一次PBFT。

为了让参与叶子保持统一顺序，采用固定配对：三层树 `C1+C2 → R1 → C3+C4 → R2`；三个协调层 `C1+C2 → M1+M2 → R1`。每个非Root自身祖先按同层连续两块分组，Root每轮一块，非祖先不参与。两个块对某个叶子都适用时，业务数组含两个证书；只有一个适用时仍验证两块的完整位置证明，业务只执行适用块。不能合并跨层、跨pair或缺尾块的业务。

当前事务仍逐块按顺序执行：第一块witness到齐后纯计算结果，第二块的读记录使用该结果的KV/seen overlay。两块witness都到齐前，正式状态、applied、stream cursor和ACK保持原值；完整后一次更新叶子序号，分别产生两个业务块的完成证明。SYNC和日志支持有序多witness，checkpoint清除本地预览缓存。31个空前缀与两块业务遇到32proof上限时先用一次纯控制PBFT消费前缀，不允许省略业务或永久阻塞。

Saguaro、SharPer、AHL协议和原始配置未做优化；新字段在baseline启动时剔除。共享源码增加Arbor执行支持和诊断后一次重新编译四个节点，所有方法同一编译参数。原1:1仍是普通Arbor启动配置，合并仅由新配置显式启用；默认测试只运行原1:1和三个baseline；双块实验需显式选择。

## 验证预算

```bash
python3 -B scripts/benchmark_quick.py --skip-build --rate 2000 --budget 240 \
  --cases lower_first lower_bundle saguaro sharper ahl
```

只运行一次200笔正确性及一次1000笔性能组，5个配置串行，使用各自新状态和同一unsigned输入，统一请求批10笔、seed42。输入速率2000 TPS给吞吐提升留出发送空间，避免沿用1000 TPS供给上限去判断倍数目标。单case60秒、无完成进展15秒，异常立即INVALID、停止后续、不重试，无故障注入，不开展万笔实验。

99项Python检查通过；266项原生真实签名/QC/PBFT顺序、双块原子性和SYNC/checkpoint检查通过（执行4.19秒）。服务器短测全部PASS，总耗时 69.02 秒；10个case完整完成、所有副本收敛且排空，view_changes=0、活动期network_failures=0，无重试或额外性能组。

|---|---:|---:|---:|---:|

| Arbor原1:1 | 753.71 | 0.6974 | 0.9771 | 1.1209 |
| Arbor两低层块合并 | 466.99 | 0.6049 | 0.8752 | 1.7199 |
| Saguaro | 528.92 | 0.4535 | 1.0543 | 1.6277 |
| SharPer | 376.22 | 0.8049 | 1.4618 | 2.0412 |

两块合并TPS降低38.04%，平均延迟降低13.26%，p95降低10.42%，p99升高53.43%。原1:1本轮相对Saguaro/SharPer/AHL分别为1.43/2.00/2.56倍，合并方案为0.88/1.24/1.59倍。输入速率已从上一轮1000提高到本轮2000，不能把原1:1 753.71与上一轮542.27直接当作代码优化收益。这里是1000笔有限负载的一次短测比值，不是稳定容量或正式论文统计结论。

合并没有达到用户期待的提升，保留为显式实验配置，普通Arbor仍使用原1:1；不开展10000笔实验。

## 瓶颈证据

6个叶子主副本总计执行的业务协调块都为39个；原1:1使用39个业务PBFT，合并使用31个，其中8个双业务合并槽，确实节省8次共识（20.51%）。四副本提交日志独立审计对应156个业务块、156→124个PBFT槽、32个双块槽，全部验证通过。

| 每叶子主副本本轮累计观测平均 s | 原1:1 | 两块合并 |
|---|---:|---:|
| 等待Root | 0.4377 | 0.0000 |
| 等待Child | 0.0000 | 1.0518 |
| 等待witness | 0.3725 | 0.4039 |
| 等待本地PBFT槽 | 0.1159 | 0.0927 |
| 调度/证明验证 | 0.0610 | 0.0906 |
| 事务执行 | 0.0212 | 0.0214 |

业务PBFT等待平均只节省0.0232秒；合并产生的Child等待达到1.0518秒，远超节省。事务计算约0.021秒，既有witness依赖约0.37–0.40秒并未随合并减半。frontier证明218→288（+32.11%），字节1,370,689→1,550,592，调度/验证0.0610→0.0906秒。

两个样本的Root业务都恰好位于Root13–17，每块10/20/5/10/5笔。原1:1在Root13–17之前要求Child13–17；合并的固定配对在Root13–17之前要求Child26/28/30/32/34。Root和Child生产节拍仍接近，Root消费要求的低层高度增长更快，合并省下的叶子共识无法消除这个等待。

| 交易组 | 原1:1平均延迟 s | 合并平均延迟 s | 原1:1最后完成 s | 合并最后完成 s |
|---|---:|---:|---:|---:|
| 同cluster950笔 | 0.6936 | 0.5482 | 1.3175 | 1.1910 |
| Root协调50笔 | 0.7698 | 1.6815 | 1.2552 | 2.1315 |

局部交易确实更早完成；完整负载TPS被50笔Root交易长尾拉低。等待分类是事件循环头部阻塞归因，不代表单独网络延迟；busy计时与等待观测区间重叠，不要相加。这里没有记录更多CPU剖析或将微小单样本差异归为稳定提升。

下一步的重点应是协调者生产高度和统一执行轮次的匹配，以及实际跨片witness等待；继续增加低层块数会放大当前Root高度等待。该方向需要单独设计与验证，本轮没有顺带扩展新策略。

服务器证据：`/root/tanghaibo/simulateHieraChain/test-results/server-two-block-bundle-20261012/summary.json`；本地工作区 `two-block-bundle-20261012/` 包含summary、真实提交审计、Root逐笔长尾、分项计时和源码/配置哈希。

只读独立审查确认：正常执行和SYNC路径按顺序使用overlay，全部witness到齐后才原子应用，没有发现导致本轮额外等待的实现缺陷；当前瓶颈是明确的2:1物理高度约束及仍需顺序收集witness。
