# Arbor 跨片组批修复

旧实现按请求 ID 遍历等待队列，遇到不同参与分片集合便结束当前批次。局部性负载逐请求随机选择参与方，因而即使 `cross_shard_batch_size=100`，也经常只提出10或20笔交易。旧负载 ID 带有参与方组号，按 ID 排序恰好把相同参与方聚在一起，掩盖了这个问题。

## 选择规则

协调者按参与分片集合选择业务批次，跳过队列中的其他集合，合并当前集合的完整客户端请求。常规提案按一个参与集合组批；单个客户端请求本身包含混合参与集合时，仍保留原有独立成批处理。总交易数不超过 `cross_shard_batch_size`；已签名请求不拆分，交易去重和冲突检查保留。

在已具备提交条件的参与组之间轮转。同组按入队先后选择完整请求，入队时间相同才用请求 ID 作为稳定次序；装不下的请求保留到下一批，可以继续寻找能装下的后续请求。满批可以立即提交；如果同组还有合法请求，却已无法装入剩余容量，也可立即提交当前批，例如上限64、请求各10笔时先提交60笔。其他未满批使用该组候选请求的入队时间判断 `cross_shard_batch_wait_ms`，其他组提交不能重新计算它的等待起点。这既避免稀少参与组阻塞满批组，也避免稀少参与组长期得不到提交。

本地缓存保存请求的参与集合、交易标识、摘要和入队时间，避免每次轮询反复序列化、计算全部等待请求的哈希。请求增删、复制状态变化和状态恢复会更新或使缓存失效。缓存仅帮助主节点选择提案，所有副本仍执行原有签名、去重、批大小和共识证明验证。

多层同步仍使用原有轮次、水位和祖先证明。在等待凑批时，本地业务只有就绪才主动请求新轮次；外部已经请求的轮次仍可通过空水位批关闭，避免等待凑批反复生成空共识，也避免挡住其他协调者的必要同步。

本次修改限定在 Arbor 的组批和提案接收。客户端发送方式、负载生成器、网络延时、PBFT 参数、叶子分片单批执行限制和协调者最多8个未完成排序批次的限制保持原有行为。Saguaro、SharPer、AHL 的协议路径不采用本次选择器。

## 落后副本的提案接收

大批次验证中发现旧接收路径的恢复问题：某副本前一批尚未应用时收到下一序列提案，状态相关的验证暂时不通过，提案被直接丢弃；主节点已完成该批后不会继续重发。该副本因此需要通过 SYNC 获取历史结果，并可能先进入孤立的换主等待。

Arbor 将窗口内、当前视图、签名及摘要合法的此类提案保存在独立缓存中。缓存条数受共识窗口限制，总字节最多16 MiB；同序列的不同摘要不能替换原提案。前序应用结束后只重试下一个序列，必须重新通过完整验证才能发送 PREPARE。没有状态进展时重试最多每100毫秒一次，旧视图或已经应用的提案清理掉。

缓存重试发生在消息处理及完整应用流程返回后，避免递归执行破坏前一批的日志和检查点。它不改变换主超时、法定票数或执行顺序，不允许未经验证的提案进入可投票 slot，也不允许取消已经发出的换主承诺。

## 验证和运行

编译并检查组批选择及真实集群收敛：

```bash
make test-arbor-batching
```

仅运行无需启动集群的选择、安全及恢复检查：

```bash
make test-arbor-batching-unit
```

重放之前生成的同一份负载，保留其中的交易、请求顺序、速率和超时参数：

```bash
make build/bin/arbor_node
python3 -B scripts/benchmark_mixed.py \
  --config config/three_layer_locality.json \
  --workload test-results/compare-all-20261005-190251-e9a86214/shared-workload.json \
  --method arbor --drain-timeout 60
```

该命令会启动独立集群，完成后检查交易确认、副本摘要、队列排空，再停止集群。结果保存到新的 `test-results/mixed-arbor-*` 目录。以上旧负载路径需要仍然存在；`make clean` 会删除 `test-results`，需要长期保留的负载和结果应先另行保存。

重新生成并比较四种方法：

```bash
python3 -B baseline/compare_all.py \
  --config config/three_layer_locality.json \
  --ahl-config config/ahl_two_layer_locality.json \
  --count 10000 --rate 5000 --batch 10 --seed 42 \
  --cross-cluster-ratio 0.05 --three-shard-ratio 0.10 \
  --repeat 3 --timeout 180 --drain-timeout 60
```

性能验证应同时统计实际业务批大小和共识批数。使用相同批大小配置并不意味着不同实现实际拼出的批次相同。
