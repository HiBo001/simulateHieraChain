# SharPer 请求停滞排查与修复（2026-10-05）

## 观察到的现象与复现范围

用户截图中，客户端已提交 10000 笔交易，完成数停在 7140，等待超过两分钟仍无进展。截图没有显示方法名，当前工作目录也没有保留该轮节点日志，因此不能直接认定该截图的根因。

使用当前版本和同一份保存的局部性负载重复测试，SharPer 在第三轮出现了可独立复现的持续停滞：只完成 8700/10000，直到 180 秒超时。前两轮完成全部交易。Arbor 用同一份负载连续八轮全部完成并通过副本一致性检查；这只能说明本次未复现 Arbor 的停滞。

负载为 10000 笔跨片交易：90% 两方、10% 三方，只有 5% 跨 cluster；六个叶子为 1、2、8 和 3、4、9，父亲分别是 5 和 6，根为 7。客户端每个请求 10 笔，速率 5000 笔/秒。跨片业务批上限 100，等待 600 ms；片内 PBFT 块上限 1000、等待 10 ms，换主超时 2000 ms。复现与修复后验证使用同一份输入，不通过调整超时、网络延时或批大小掩盖问题。

## 1. 发起批次与本地序号预约之间的竞争

旧代码构造自身 `SH_SUPER_PROPOSE` 时签定 `origin_seq = applied + 1`，随后记录并广播请求，却直到下一次事件循环才建立本片 claim 和 assignment。这个间隙允许外来批次先占用相同的本地序号。

外来批次执行后 `applied` 增加，自己已经签名的 `origin_seq` 过期。后续 `sharperPropose()` 一直跳过该批，而 `shInitiating` 又阻止发起新的客户端批次。延长等待时间无法使其恢复。

失败轮中，分片 2 最后一个自身批次位于序号 18，后续序号 19～34 全部是外来批次；分片 4 最后一个自身批次位于序号 15，后续序号 16～37 也都是外来批次。两片分别留下 65 个客户端请求，合计对应未完成的 1300 笔交易。首次换主前没有消息验证拒绝；换主发生在业务已经停止推进之后。

修复将原本的本地预约逻辑抽成 `shAssignLocal()`。发起片在构造并广播 SUPER_PROPOSE 的同一个串行处理步骤中立即建立本地 claim、assignment 和 ACCEPT；处理下一条网络消息前，已公布的序号就已经被预约。

## 2. NEW_VIEW 后未选中的弱预约没有释放

共享 PBFT 代码安装 NEW_VIEW 会清理旧 slots，但旧版 SharPer 仍保留 `shLocal`、assignment 和 ACCEPT。如果该预约没有全局 prepared 证明，也没有足够的恢复支持，没有被新视图选中，它仍可能挡住后续合法请求。

修复使用已验证的 NEW_VIEW canonical values 判断旧预约是否保留：

- 已应用的批次保持原状态。
- 已发出本机 COMMIT 的批次保持原承诺，不删除或改写 COMMIT。
- 新视图选中的原值保留原 claim。
- 其余未提交的旧弱预约释放本地 assignment、ACCEPT 和旧本片票集，但保留相同的签名批次、完整请求、去重信息，并重新加入待处理队列。

新主如果恢复的是自己已经签定的 origin head，且该 head 没有被 canonical values 占用，就在安装 NEW_VIEW 的同一步重新预约同一个批次。它不修改原 `origin_seq`、批次 ID 或签名请求，避免恢复后再次出现外来批次抢占这个序号的窗口。

## 3. 新视图已有证明，却没有恢复全部参与方 ACCEPT

旧恢复路径只导入本片预约中的 ACCEPT。某个第二参与分片的新主如果之前没有收到低 ID 参与方的票，即使 VIEW_CHANGE 已经携带完整的全局 prepared 证明，也仍然无法满足接纳 assignment 的 prefix 检查。

修复只导入与 canonical 序号和值完全一致、通过 `validPrepared` 和完整 `shAcceptVector` 验证的证明。恢复所有参与片按签名者区分的 ACCEPT 票，不降低票数要求，不混合不同 claim。如果本机已经发出 COMMIT，导入向量还必须匹配原 COMMIT 的 `seqs/claims`；不匹配时保留原向量。

## 4. 超时与本机提交承诺保护

低 ID 前缀补齐时，原代码已经会开始新的本地处理等待期限。此次保留这一逻辑，并测试第三份有效 ACCEPT 激活计时、重复提案和重复 ACCEPT 不刷新期限；没有把已有正确行为当作新的修复。

在 `installStable()` 和 `slots.clear()` 之前检查本机 COMMIT：只有同时具备完整有效 prepared 证明、全部参与方 ACCEPT 向量，并且原 COMMIT 与向量一致时，才认为存在必须保留的承诺。遗漏或冲突的 NEW_VIEW 整体拒绝，不允许部分安装；单份未经完整证明支持的 COMMIT 不能制造新的锁。

## 协议范围

这些变更修复预约、恢复证据使用和计时问题。没有新增共识阶段，没有修改 3/4 投票门槛、当前参与方预约顺序或通用批次调度。Arbor、Saguaro、AHL 的预处理后协议源码在修改前后逐字节一致。

本次不实现完整 SharPer Algorithm 4 跨片取消与重新提案机制。复杂故障恢复中，如果 canonical 另一批次占用了旧 initiation 的 `origin_seq`，仍不能擅自改写已经签名的序号或取消已经投 COMMIT 的批次。本次验证不代表该实现已经覆盖论文的全部 Byzantine 故障路径。

