# SharPer 论文机制与当前实现边界（2026-10-06）

本次检查针对用户要求：SharPer 基线应尽量遵循论文，不再增加论文没有提出的跨片调度优化。性能排名不是判断依据，不能为了让 Arbor 吞吐更高而给 SharPer 加等待或降低其共识效率。

当前基线保留论文 Byzantine flattened 的全参与片 ACCEPT/COMMIT 路径、论文允许的块批处理和高负载 `SUPER_PROPOSE` 变体；移除整条客户端等待队列按参与集合聚类，以及请求 ID 决定新批次顺序的行为。通用认证、网络和已确认的正确性修复继续保留。升序预约、固定最小发起片、单个未执行跨片 slot 等既有实现限制还在，因此当前版本仍应称为**有界工程实现**，不能称为完整 SharPer 复现。

## 2. 本轮删除的额外组批行为

旧 `sharperPropose()` 遍历按请求 ID 排列的 `pending`。确定一个参与集合后，遇到不同集合或其他无法选取的请求会跳过，并继续寻找后面的同集合请求。这可能把原先非连续到达的多个请求凑成一个更大的跨片批次。论文的“允许连续跨片交易组块”不足以证明这种跨队列重排具有论文依据。

现在增加独立的本地接纳次序索引。请求第一次成功进入 pending 时取得位置，网络重传和相同请求不取得新位置，请求完成后清理位置。恢复待处理索引时，仍待处理的请求保留原位置；deferred 请求只在真正接纳到 pending 时取得位置。请求 ID 保留用于查询、去重和冲突检测。

选批只取尚未提议的新客户端请求中的连续同参与集合前缀，遇到以下情况即停止：

- 下一请求属于不同参与集合。
- 加入完整请求会超过原批容量。
- 下一请求因依赖而暂时不可执行。

不拆开原签名请求，不越过边界寻找后面的同组请求。已属于在途批次的请求不再次选批。这是本副本的 pending 接纳顺序，不保证不同副本看到完全相同的网络到达顺序，也没有修改已经签名的跨片批次内容或把所有 `shPending` 跨片提案强制改成全局 FIFO。

论文并未要求客户端必须使用严格 FIFO；本次选择连续前缀是去除额外重排的保守实现方式，不应再把它宣传成论文新机制。

### 原等待参数的处理

普通 `batch_wait_ms` 门槛保留。对于不足额的跨片前缀：

- 若队尾仍开放，可以继续等待新到达同组请求，使用原 `cross_shard_batch_wait_ms`。
- 若已经遇到不同组、容量或不可执行边界，前缀不能继续增长；满足原普通等待后即可提议，不能靠等待后面的同组请求再越过边界凑批。

满批按原规则提议。没有新增等待参数、低吞吐配额或仅对 SharPer 生效的额外网络延时。批大小变化是连续前缀规则的自然结果，不能据此人为给某个方法调速。

## 3. 保留的论文机制

### SUPER-PROPOSE 高负载变体

`sharperPropose()` 发送 `SH_SUPER_PROPOSE`，参与片主节点用 `shAssignLocal()` 分配本地序号，并向本片广播包含签名 claim 的赋值。源码复用 PREPREPARE 的消息格式和本地日志槽；这个载体对应高负载变体中由本片主节点确定序号、传播给本片副本的作用。

跨片路径没有在这个赋值外再运行一轮普通本片 PBFT 的 PREPARE/COMMIT。`sharperHandle()` 不把普通本片 PREPARE/COMMIT 当成跨片投票；跨片投票由 `SH_ACCEPT` 和 `SH_COMMIT` 直接完成。因此应依据消息作用审查，不能仅看到 PREPREPARE 名字就认为它减少或增加了必要的独立共识轮次。

### 全参与片的法定人数

每片四副本、`f=1` 时：

1. `shAcceptVector()` 要求每个参与片至少三个不同签名者的匹配 ACCEPT，并检查同片 claim 一致。
2. `sharperAdvance()` 只有得到完整 ACCEPT 向量，才能发出本机 COMMIT。
3. `shCommitRecords()` 要求每个参与片至少三个不同签名者的匹配 COMMIT，检查共同的序号、claim 向量及同片读取记录一致。
4. 完整证书形成后才按本地序号执行；自己的读取记录还要与真实状态一致。

这对应 Algorithm 3 的每参与片 `2f+1` 门槛。没有把三票降成两票，没有仅收发起片的票，也没有让主节点单独决定跨片提交。缓存不会提供额外投票。客户端最后仍要求两个不同发起片副本的匹配回复。

### 批处理

论文允许组块，因此保留 `cross_shard_batch_size` 和组批等待，并非省略共识。一个业务块中的每个请求保持原客户端签名，每笔交易仍逐笔进行真实执行和去重；一个共识批的票数要求不会因包含多笔交易而降低。

连续前缀还要求同一参与集合，这是为了让一个全参与方共识块具有同一组参与片的实现选择；论文脚注没有逐项规定这一组批约束。应披露它，不能把它与原先跨队列聚类混为一项。

## 4. 保留的通用工程与正确性修复

### 完整签名消息、证书的验证缓存

`shSigned()` 用完整消息序列化指纹复用此前通过的成员签名验证；`sharperValidCertificate()` 用完整证书指纹复用此前通过的全参与片证明检查。首次仍验证签名、参与方、请求摘要和法定人数；改变正文、签名或证书内容不能复用旧指纹。

这些缓存避免对同一份不可变数据反复做相同验证，不合并参与片，不减少消息阶段。当前完整客户端请求仍经过 `sharperValidRequest()`；不能把仅按请求 ID 命中当成请求内容已经认证。与真实状态相关的 ID 冲突、去重、读取状态和顺序检查在正常处理或执行路径继续进行，不用旧缓存替代。

Arbor 和 Saguaro 也保留各自的有效证明缓存。这类方法属于通用工程实现，但并不表示各方法的缓存内部代码和成本完全相同；比较结果仍应保留配置、二进制、输入和完整完成证据。

### 共享 PBFT 恢复去重

已经完整认证、并收集到原恢复证据中的 VC，只有整个信封的序列化指纹完全匹配，才提前丢弃重放。新消息仍按原规则验证；NEW_VIEW 仍包含三个不同成员的有效 VC 和恢复提案，每个目标 view 保留一个已签候选并重传它，首次真实 prepared 推进阶段计时。

这项共享修复在四个方法中保留，解决重复恢复验证、候选反复构造和超时计时问题，不替代 SharPer 的全参与片 ACCEPT/COMMIT，也不使未经认证的预约成为提交证据。

### 已修复的预约与恢复错误

发起片在公布已经签定的 `origin_seq` 的同一步预约本地槽，防止后续外来提案抢占该序号；换主恢复时保留完整已签请求和已经投出的 COMMIT，释放未提交且未被新 view 选中的弱预约，导入选中完整 prepared 证明中的全部参与方 ACCEPT。

这些修复保持原签名批次及承诺，没有给请求改写新的签名序号，也没有降低门槛。详细过程继续保留在 `docs/SHARPER_STALL_FIX.md`。

### 网络、执行与完成确认

持久 TCP、认证消息重传、客户端 f+1 初发与故障重试、增量状态摘要及共同 Fibonacci 业务执行保留。不能通过每条消息重新建 TCP 或故意反复验同一份签名来模拟“论文更慢”。

`SH_EXECUTED` 是当前项目增加的实际执行完成通知：发起片收齐每参与片三个匹配执行通知才回复，客户端再要求两个匹配回复。论文正常 Algorithm 3 没有这个额外完成通知步骤；它为公共实验的“所有相关叶子已经实际执行”统计口径服务，不承担新的排序或 2PC 决定权，且会增加等待成本。不能把含这个步骤的端到端延时称为原论文三阶段延时的直接测量。

## 5. 仍保留的论文差异与边界

| 当前实现选择 | 与论文的差异及影响 |
|---|---|
| 最小参与片固定发起 | 论文允许客户端发送到参与片，由该片成为 initiator，并未要求总是最小 ID。当前是确定性路由选择，会影响发起负载分布，应在实验中说明。 |
| 参与片按 ID 升序预约 | `shPrefixReady()` 要求所有更低 ID 参与片的三份 ACCEPT，才允许本片预约。原文按 ID 排列序号向量不是这项等待规则。它提前避免资源环，但把原本可并行的本地分配串联起来，增加预约等待。 |
| 每片一个未执行跨片 slot | `shLocal` 和队首检查限制本地在途预约；发起片还有 `shInitiating` 完成等待。它让读取状态与顺序容易保持一致，但比论文针对重叠参与集合的等待条件更保守，限制并行度。 |
| Algorithm 4 和跨片故障归因未完整实现 | 当前恢复覆盖既有回归路径，不包含原文全部冲突 ACCEPT 撤回、重新排序、SUPER-ACCEPT 和事务级故障查询场景。不能保证所有保持心跳却故意分裂预约或扣消息的 Byzantine 调度最终完成。 |
| SH_EXECUTED 完成确认 | 属于实验完成口径适配，增加通知与等待；不是原文列出的正常三阶段之一。 |

直接删除升序预约的检查，不等于得到原论文并行协议。不同参与片可能按不同顺序持有未提交的槽，形成循环等待；需要按 §4.3 / Algorithm 4 完成冲突处理，并正确保护已经投出的 COMMIT。放宽单 slot、改变发起选择或删除完成通知，也会改变调度、恢复或统计口径，需要各自设计和验证，不能作为本轮组批修改顺带实施。

现有限制通常增加等待或限制并行；不能把它们描述为让 SharPer 无条件获益的优化。同样，SharPer 在某种局部性负载下最快，也不能反推一定使用了论文外加速。论文允许无重叠参与集合的跨片交易并行，负载参与区域、链路和批大小都可能影响排名。

## 6. 本轮变更范围与验证记录

本轮生产行为修改只涉及 SharPer 尚未提议的客户端请求接纳顺序、连续前缀选择及对应等待判断。原 unsigned 工作负载、交易内容、签名、参与方投票、执行和已签跨片批恢复不因本轮修改而改变。Arbor、Saguaro、AHL 的对应预处理协议源码保持逐字节一致；共享 PBFT 的上一轮修复继续保留。

验证应检查本地 FIFO 与边界行为、重复请求不改变位置、完成后的清理、恢复后的顺序、有效投票门槛、原预约恢复回归，以及同一保存负载的完整执行。采用不同本地到达次序的主节点只改变它提议的合法顺序；其他副本依据签名和证书验证该提案，不要求它们的本地等待队列与主节点完全相同。
