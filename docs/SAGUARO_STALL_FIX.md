# Saguaro 混合跨片负载卡顿修复（2026-10-04）

## 原问题与证据

原用例有 10000 笔交易，9000 笔跨两个叶子分片、1000 笔跨三个叶子分片；客户端每个请求 10 笔，目标发送率 5000 tx/s，超时 180 秒。负载涉及 `[1,2]`、`[1,3]`、`[2,3]` 各 3000 笔和 `[1,2,3]` 1000 笔。

三层拓扑为根 7，子协调片 5/6，叶子 1/2 属于 5，叶子 3/4 属于 6。NCA 5 协调 3000 笔，NCA 7 协调 7000 笔。叶子 1/2/3 各执行 7000 笔；叶子 4 不参与。全部 7 个分片启动 28 个真实 PBFT 节点。

原运行只完成 5640 笔，之后约 90 秒没有新的客户端完成。叶子存在已收到却未提议的 PREPARE，另一参与方持有相应锁，根协调片还有大量待完成请求。排查确认：

1. 计时使用上一轮进展时刻。空闲或等待远端超过 `view_timeout_ms` 后，新 INIT/DECISION 入队就立刻触发换主，尚未给这一轮正常 PBFT 留出时间。
2. VIEW_CHANGE 包含完整稳定状态，NEW_VIEW 再包含多个 VIEW_CHANGE。历史膨胀后消息越过原来 16 MiB 的传输限制；某叶子的稳定元数据已有约 17.2 MB，另一叶子三份元数据已约 23.9 MB，尚未计完整信封。恢复消息被丢弃后无法恢复进展。
3. 协调者连续发送八个带重叠 key 的批次，造成大量自冲突 ABORT，立刻重试又产生新的冲突和历史记录。原 NCA 5/7 分别累计 203/289 个 ABORT。

原结果是不完整执行，不能用其 TPS 与修复后的完整执行结果计算性能提升倍数。

## 代码修改

### 新阶段的计时

对真正新收到且通过验证的 CLIENT、INIT、DECISION，以及使 DECIDE 就绪的新投票，判断它是否把分片从等待/空闲变为有可执行工作。如果是，并且当前没有未应用的 PBFT 提案/证书、没有正在换主，就从当前时刻开始计时。

重复消息不刷新计时；本地 PBFT 已卡住时，新客户端请求也不能掩盖这个超时。收齐首份有效完整 ACK 集合属于真实进展，释放调度 key 后可以唤醒等待请求。恢复状态完成后按恢复结束时刻计时，避免大量历史索引重建本身消耗后续 PBFT 期限。

### 恢复消息压缩

`source/network.h` 保留普通 JSON 的原始四字节长度加正文帧。只有正文超过 16 MiB 时使用新压缩帧：长度最高位标记压缩，正文包含四字节解压长度和 zlib 数据。线路单帧上限仍为 16 MiB，原始 JSON 上限为 128 MiB。

接收器分块解压，检查声明长度、实际长度、压缩流完整结束、校验和、尾部多余字节和资源上限。恢复原 JSON 后才进入原有 Ed25519 签名验证。无效连接不阻塞其他正常连接，网络错误计数保留。持续 TCP 连接、附加网络延时、每对端和全局积压字节上限仍生效。没有删除检查点历史、阶段记录、签名或去重信息。

所有节点必须使用重新编译后的同一版本启动。Linux 构建增加 `zlib1g-dev`；macOS SDK 提供 zlib。128 MiB 解压限制仍是有限实验的边界，历史状态不会因此变成无限可扩展。

### 本协调者冲突避让与退避

每个 NCA 为在途批次保留 `(叶子分片, key)` 集合。选择新请求时跳过与已在途批次冲突的请求，继续收集不冲突请求；同一业务批次内部可继续按顺序访问同一个 key。最多八个不冲突批次在途，直到收齐全部 ACK 后释放 key。

不同 NCA 之间仍按真实叶子锁处理冲突，投 NO 后经过 DECIDE ABORT、FINISH、释放锁和全部 ACK，再重试完整原请求。失败次数在复制的 DECIDE 中记录；调度采用 50–849 ms 的确定性指数退避和请求 ID 抖动，上限不超过共识超时的一半。退避和 key 预留只影响选批，不影响 PBFT 值有效性。

同时把 INIT 交易去重有效性与异步 ACK 分离：未决定交易索引只由复制的 INIT/DECIDE 更新，恢复时由复制状态重建。各副本 ACK 到达时刻不同，不会让它们对同一个 INIT 提案给出不同判断。

### 进度与混合负载复测

共享客户端每 5 秒输出提交/完成交易数、确认请求数和运行秒数；最终 TPS、平均及分位延时的统计口径不变。

新增 `scripts/benchmark_mixed.py`，直接复用已有 unsigned workload。它按每个请求真实参与方和 NCA 推导预期计数，自动启动/停止独立集群。只有客户端完整确认、所有副本计数正确、KV/状态/链摘要收敛、队列和 Saguaro 锁排空，且没有超限、解析、队列或收件箱丢弃错误时，才输出 PASS 和有效 TPS。

客户端取得两个匹配回复即可结束监听；其余节点迟到回复可能增加网络连接/写失败。因此工具保留这些原始计数并提示核对，不单凭总失败计数否定已完整收敛的执行。

## 测试与复测指令

在项目根目录执行：

```bash
make
make test

python3 scripts/benchmark_mixed.py \
  --config config/three_layer_cross100.json \
  --workload test-results/mixed-90-10/shared-workload.json \
  --method saguaro

python3 scripts/benchmark_mixed.py \
  --config config/three_layer_cross100.json \
  --workload test-results/mixed-90-10/shared-workload.json \
  --method arbor
```

负载路径指向已有的原测试文件，两个方法复用相同交易 ID、参与方、读写 key、数值、请求顺序和发送速率。工具自动使用空状态和临时空闲端口，不改变 `runtime/latest`。每次保留单独结果目录，包含实际配置、完整输入、客户端进度/结果、开始和结束状态、汇总。

新增回归覆盖空闲后首次 PREPARE、远端长等待后的 DECISION、同一协调者八批共享 key 的准入、重复 INIT 不掩盖真实超时。故障计时测试只暂停一个主节点，遵守四节点 PBFT 的 `f=1` 范围，恢复后仍核对全部四副本状态与锁排空。网络回归实际传输并验证 40 MiB 签名消息，另检查恶意压缩帧、截断、长度不符及正常小帧兼容。

`view_timeout_ms` 需要大于组批等待及正常共识处理时间，并为机器调度、实际计算和网络延时留出余量。此修复不改变传统 2PC 阶段，不增加投机执行流水线，也不改变此前的客户端 f+1 初发、去重、持久 TCP、forward 聚合和状态摘要优化。

## 本机验证结果

在 8 核 macOS/arm64 机器上顺序运行，原有 Arbor 回归通过，最终 Saguaro 14 项回归及混合负载工具 13 项单元测试全部通过；网络 8 组和状态摘要 5 组 C++ 验证通过。首次计时故障测试使用了超过 f=1 的暂停方式，已更正为仅暂停主节点，并重新完整运行 Saguaro 测试。

| --- | ---: | ---: |
| 完成交易 / 请求 | 10000 / 1000 | 10000 / 1000 |
| 完成 TPS | 255.348 | 659.120 |

| 全部 28 副本收敛排空 | PASS | PASS |

两轮输入负载的 SHA-256 均为 `3110cbc6875a7b8147d034ca60a2a4b81add6c1a442b7d810909273c3ed2ee55`，未改变 timeout_s=180 或 rate=5000。Saguaro NCA 5/7 本轮 ABORT 为 30/50，最终全部重试成功；不同 NCA 冲突仍真实执行 ABORT，未掩盖失败成本。本表是单轮完整执行验收，不能代替论文多轮稳定性实验。
