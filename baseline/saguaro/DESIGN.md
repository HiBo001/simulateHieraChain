# Saguaro：NCA 协调的传统 2PC 实现

## 1. 目的与共用组件

这个基线用于回答：在相同交易负载、相同分片拓扑、相同本地共识和执行成本下，Arbor 与传统 2PC 处理跨片交易的吞吐和延时有什么差别。

Saguaro 是本项目给基线起的名字。协议采用传统 prepare/vote 与 decision/finalize 两阶段提交，不包含 Arbor 的多层排序传播、协调者轮次封闭或叶子 frontier 机制。本实现没有声称复现外部同名论文的全部协议。

Saguaro 复用 `source/main.cpp` 的 PBFT、Ed25519 消息认证、交易验证、客户端、网络、检查点、视图切换、状态摘要和统计代码。`baseline/saguaro/main.cpp` 选择 Saguaro 的业务处理钩子，`protocol.inc` 实现这些钩子，编译为 `build/bin/saguaro_node`。Arbor 仍编译为 `build/bin/arbor_node`，通过原有业务路径运行。

同一配置仍为每个分片启动四个独立节点进程。PBFT 的 PRE-PREPARE、PREPARE、COMMIT 消息实际通过 TCP 传输；节点需要有效的本地共识证书才能应用一个阶段。分片间消息使用同一网络实现和配置的链路延时，执行也实际调用 Fibonacci 计算。

## 2. 协调者与通信路径

跨片交易的参与方由交易的 `participants` 字段指定，参与方均为叶子分片。每个参与方访问自己的 `accesses` 项，key 的分片归属必须与该项一致。客户端请求的目标分片必须等于这些参与方的最近公共祖先。

例如两层拓扑 `1 -> 5 <- 2` 中，交易 `[1,2]` 的协调者为分片 5。三层拓扑 `1,2 -> 5 -> 7`、`3,4 -> 6 -> 7` 中，`[1,2]` 由 5 协调，`[1,3]` 和 `[1,2,3]` 由 7 协调。

协调者直接与实际参与叶子通信，未参与的中间分片不额外执行 2PC。这是此基线的协议定义。参与方数量、NCA 深度和配置中对应链路的延时都会影响成本，比较结果需要同时记录拓扑和参与方集合。

每个分片由当前 PBFT 主节点担任 forward。副本完成某个阶段的本地 PBFT 后，对相应语义记录的 `record_digest` 签发 `SAG_ATTEST`；forward 收齐三个不同副本对完全相同记录摘要的签名，构成阶段证明，再用 `SAG_QC` 向目标分片发送。证明中完整记录仅传一份，三份签名投票携带摘要，避免大读写集重复编码传输。目标分片验证消息与证明，再进入本地共识。这种阶段证明来自已提交状态，不能代替本地 PBFT；本地完整 PREPARE/COMMIT 证书仍保存于提交日志。签名集合不会进入复制的业务状态，避免副本收到不同有效签名子集时状态摘要不一致。客户端初始只发给 `f+1 = 2` 个副本，超时重试扩大到四个副本，保留既有去重路径。

## 3. 正常提交过程

| 顺序 | 位置 | 实际处理 | 对应用状态的影响 |
| --- | --- | --- | --- |
| 1 | NCA 协调分片 | 对完整请求批次运行 PBFT，记录 `INIT` | 创建业务批次，不修改叶子 KV |
| 2 | 每个参与分片 | 验证 INIT 证书；对 `PREPARE` 运行 PBFT | 取得本地锁，保存读集、写入意图和本地计算结果，返回 YES/NO |
| 3 | NCA 协调分片 | 验证全部参与方投票；对 `DECIDE` 运行 PBFT | 全部 YES 时形成 COMMIT，否则形成 ABORT |
| 4 | 每个参与分片 | 验证决定证书；对 `FINISH` 运行 PBFT | COMMIT 写入本地 KV；ABORT 丢弃暂存；释放锁并回复 ACK |
| 5 | NCA 协调分片 | 收集所有实际参与方最终 ACK | 更新完成记录并向客户端回复 |

INIT 与 DECIDE 是协调者的两个不同本地共识批次；PREPARE 与 FINISH 是参与方的两个不同本地共识批次。即使配置了多个交易组成业务批次，也不会把上述阶段合并成一次虚构的共识。

协调者收到全部最终 ACK 后直接结束，不再为 ACK 增加一次共识。客户端需要来自目标协调分片两个不同副本的匹配、已认证回复，之后才统计该交易完成。

一个跨片交易在两个参与叶子各执行一次，是两个分片的执行计数；客户端 TPS 中只算一笔完成的交易。协调分片记录跨片业务数量和最终完成数量，不冒充执行叶子的业务计算。

## 4. 暂存读写、锁与冲突

PREPARE 保存该批实际使用的本地读集、写入意图和 Fibonacci 计算结果。跨片 value 依赖其他参与方读值，因此 DECIDE 记录收齐的各方读写记录，FINISH 使用这些已固定的记录组装最终写入状态，不再重复 Fibonacci 执行。这些记录绑定业务批次和原始交易内容。发生正常通信重试时复用已记录的阶段结果，不能把相同交易再次当作新事务执行；发生 ABORT 后重新尝试则使用新的批次标识，重新读取当前已提交状态。

准备阶段计算的结果在最终 COMMIT 之前不出现在应用 KV 中。锁持续到 FINISH 已由参与方 PBFT 提交，片内交易也必须尊重跨片持有的锁，不能改写其读写状态。相同业务批次内连续访问相同 key 的交易按批内顺序使用逐笔更新的暂存状态，最终一次提交整个批次。

不同 NCA 可以同时发起交易。如果参与方当前持有冲突锁，准备阶段不能无限等待另一事务的决定：它投 NO，协调者提交 ABORT；所有参与方提交 FINISH 并释放暂存锁后，协调者重试尚未成功的完整请求。ABORT 不计入成功 TPS，其计算、共识与网络成本仍体现在本次客户端等待时间中。

每个 NCA 最多保留八个未完成业务批次，与 Arbor 的协调者上限一致；多个独立 NCA 也可并行。协调者维护自己在途批次占用的 `(参与分片, key)` 索引，选新批次时跳过与它们冲突的请求，继续选择不冲突的请求。同一批内的连续访问仍允许合批。索引一直保留到收齐所有参与方 ACK，保证旧批次已经释放叶子锁；它只参与本地主节点调度，不作为 PBFT 提案有效性的判据。

不同 NCA 的锁冲突仍可能导致 ABORT。协调者在复制的 DECIDE 状态中增加该请求的失败次数，收齐 ABORT ACK 后按请求 ID 与失败次数计算退避：首次 50–99 ms，随后指数增加，最多 800–849 ms，并受 `view_timeout_ms / 2` 限制。重复 ACK 不增加次数。恢复时根据复制的失败次数重建本地等待截止时间，时钟值不进入共识状态。该退避不承诺跨协调者严格公平或完全消除 ABORT。

每个分片的 PBFT 引擎仍一次只发起一个新共识批次，已完成 INIT 的业务可以等待远端投票而不占用这个本地共识槽位。这一版没有投机执行与重做流水线。对高冲突负载，需同时查看 ABORT 数量与延时，不能只比较一轮 TPS。

## 5. 消息证明、去重与故障处理

阶段消息必须通过原有 Ed25519 认证和 run ID 检查，并携带三个来源分片副本对已完成阶段记录的匹配签名证明。验证还应绑定协调者、实际参与者、批次和阶段，防止旧批次或无关分片的消息驱动当前交易。

PBFT 本地提交需要至少三个不同副本的 COMMIT，准备证明需要两个备份 PREPARE。跨片重复接收同一个阶段请求时使用批次/阶段索引，不再次发起相同本地共识。客户端重复请求和相同交易 ID 的别名请求复用执行结果，不能二次改写状态。

共识状态中的批次、准备记录、锁和决定进入状态摘要与检查点。forward 切换后按已有决定和未结束阶段恢复发送，不能重新决定一个已记录为 COMMIT/ABORT 的批次。PBFT 的状态同步继续使用共享实现。

空闲或等待远端期间不消耗下一次本地 PBFT 的期限。新的有效请求、INIT、DECISION 或补齐投票使分片首次出现可执行工作时，重新开始共识计时；已存在的同阶段消息、重复客户端请求和重试证明不会延长期限。若本地已有未应用的 PBFT 提案或证书，也不重置计时，保证真实卡住的共识仍能切换视图。收齐新的完整 ACK 集合属于实际进展，可以唤醒先前被 key 冲突挡住的请求。

INIT 的交易去重有效性由复制的 INIT/DECIDE 状态中的未决定交易索引判断，不能依赖各副本收到最终 ACK 的先后。DECIDE 释放该未决定索引；最终 ACK 另行释放本地调度索引，两者用途不同。

共享 TCP 传输对超过 16 MiB 的 JSON 消息使用 zlib 压缩帧，接收后恢复完整 JSON，再进行原有消息认证。普通小消息沿用原始帧格式。线路上的单帧仍限制为 16 MiB，解压后的 JSON 限制为 128 MiB，并检查长度、完整压缩流和校验和。此路径用于较大的 VIEW_CHANGE/NEW_VIEW 等恢复消息，不截断检查点、签名或去重历史。所有节点必须重新编译并使用同一版本启动；此界限仍不支持无限增长的历史状态。

“已记录”指本项目 PBFT 复制状态与提交日志；本项目当前不支持在原运行目录重启节点，也没有额外实现机器掉电后的磁盘恢复。应通过新运行目录启动实验。经典 2PC 在决定无法获得时可能阻塞；本实现不把超时随意当成已准备事务的 ABORT，也不声称解决超出当前故障模型的问题。

## 6. 片内交易与执行语义

片内交易仍走原来的本地 PBFT 与 Fibonacci 执行，客户端命令、结果格式和秒制延时保持一致。准备中的跨片锁会约束冲突片内交易；独立 key 的片内交易可以在合法的本地共识顺序中执行。

两个方法使用相同的应用交易语义：读取参与方当前状态，执行同样的 Fibonacci 工作，按交易确定的读写规则更新本地版本、value 和摘要。协议状态、共识批次数及链摘要可能不同；这些是两种算法的正常差异。比较性能使用相同工作负载，不要求两种协议的全部内部状态相同。

## 7. 可观测状态与结果

`status.json` 保留共有字段：执行/跨片排序/完成交易数，已应用和稳定 PBFT 批次，KV、协议状态和链摘要，消息和字节数，网络错误，视图切换，待处理请求及去重等待队列。

Saguaro 另提供 `method = saguaro` 与阶段状态：`sag_active_batches`、`sag_pending_prepares`、`sag_pending_decisions`、`sag_pending_completions`、`sag_held_locks`、`sag_aborted_batches`。新增 `sag_active_access_keys` 显示本协调者保留的访问 key 数，`sag_admission_deferrals` 累计选批时跳过的阻塞请求检查次数，`sag_work_timer_starts` 记录新工作计时次数，`sag_retry_waiting_requests` 显示尚在退避的请求数。完成测量后，业务队列和锁应排空，同一分片四个副本的状态/链/KV 摘要与执行计数应收敛。

客户端输出 `completed_tps`、`avg_latency_s`、`p50_s`、`p95_s`、`p99_s`。TPS 从本轮客户端开始发送到所有请求获得匹配结果计算；延时从对应请求首次提交到交易获得最终确认计算。中途重试仍包含在等待时间中，不把仅准备或仅决定当成完成。

## 8. 统一负载实验

`baseline/compare.py` 每个用例生成一个未签名 workload，保存后逐字复用给 Arbor 和 Saguaro。相同交易 ID、请求 ID、参与方集合、key/value、请求批量、速率和随机种子都可通过文件及哈希核对。新运行 ID、节点密钥和客户端回复端口可不同，这些差异不改变业务交易。

每个算法运行在新的目录和空状态上，使用相同拓扑、四副本、PBFT 参数、网络延时和 Fibonacci 次数；配对实验依次运行，避免两个集群争抢同一台机器 CPU。重复轮次交替先运行哪个方法，减少固定先后顺序造成的偏差。

汇总只对完整完成、无错误、所有副本计数正确且收敛排空的配对计算 TPS 比值；失败保留但不混入成功中位数。一次短测只能验证接口和协议完整性，实际性能由负载冲突、共识/请求批量、网络延时和 CPU 资源共同决定，不能预先保证某个方法更快。正式论文实验应扩大交易量、多个速率，至少三轮重复，并记录机器 CPU 核数、系统和配置。
