# AHL 实现设计

## 1. 复现定义与代码复用

本项目的 AHL 定义为“两层拓扑上的 Saguaro 2PC”：所有业务叶子直接隶属唯一上层分片，所有跨片事务由这个上层协调。用户明确要求与 Arbor 比较时保留 Arbor 的多层结构，AHL 改为两层。实现不引入其他同名系统的协议或安全假设。

`baseline/ahl/main.cpp` 定义 `ARBOR_AHL` 和 `ARBOR_SAGUARO` 后使用公共运行框架；`baseline/ahl/protocol.inc` 包含 `baseline/saguaro/protocol.inc`。AHL 复用 Saguaro 的同一份准备、决定、锁、去重、重传和恢复代码。以后修复 2PC 公共实现时两种方法同时受益，不维护两个容易偏离的协议副本。

AHL 特有的实现只涉及方法标识、拓扑校验、唯一上层路由和对比工具的双配置支持。Arbor、Saguaro 和 SharPer 的原有方法选择保持独立。

## 2. 拓扑、参与方与请求路由

合法 AHL 配置必须满足：存在且只存在一个根；除根之外的所有分片均为直接叶子；至少有两个叶子；每个分片四个副本。启动工具检查后，二进制读取实际成员配置时再次检查，防止绕过启动器传入多层拓扑。

示例 `config/ahl_two_layer.json` 使用叶子 1、2、3、4 和唯一上层 7。跨片 `[1,2]`、`[1,3]`、`[2,3]` 和 `[1,2,3]` 的协调者均为 7。事务参与方始终只是交易中指定的叶子；未参与的叶子不运行这个事务的 PREPARE/FINISH，也不执行应用计算。

客户端普通 `load` 依据当前 AHL 配置生成目标 7 的跨片请求。共享负载则依据 Arbor 多层配置生成，例如 `[1,2]` 的目标为 5、`[1,3]` 的目标为 7。AHL 客户端读取请求后，在签名前把跨片目标改为自己的唯一上层 7。原始 unsigned 文件保持不变，业务交易的内容和顺序不变；签名信封的目标、运行 ID、密钥和回复端口可以不同。

片内交易仍发到参与叶子，不经过上层。客户端初始只发送给目标分片的两个不同副本，以满足 `f+1=2`；备份转给当前主节点，超时重试扩展到四个副本。接收和转发路径沿用原有去重，重复消息不会产生新的业务事务。

## 3. 真实 PBFT 和 2PC 完成条件

每片四副本、`f=1`，使用公共 PBFT 的 PREPREPARE、PREPARE、COMMIT 消息和签名校验。跨片不是按配置延时直接模拟完成：每个阶段必须真正完成对应分片的本地共识，才产生下一阶段记录。

| 阶段 | 运行位置 | 本地共识后的处理 | 发往下一阶段的内容 |
|---|---|---|---|
| INIT | 唯一上层 | 记录原始请求批次、参与方和业务批次 ID | 各参与叶子的准备请求 |
| PREPARE | 每个参与叶子 | 检查锁、读取状态、保存写入意图并实际计算；投 YES/NO | 本叶子的准备结果和读写记录 |
| DECIDE | 唯一上层 | 收齐全部参与方的有效准备证明后，记录 COMMIT 或 ABORT | 同一个全局决定及其证明 |
| FINISH | 每个参与叶子 | COMMIT 应用已准备结果；ABORT 丢弃暂存；释放锁 | 最终实际处理 ACK |
| 最终确认 | 唯一上层 | 收齐全部实际参与方的有效 ACK 后结束 | 给客户端的最终执行结果 |

INIT 和 DECIDE 是上层的两次本地 PBFT，PREPARE 和 FINISH 是每个参与叶子的两次本地 PBFT。`p` 个参与叶子的一个正常业务批次共需要 `2+2p` 次分片内 PBFT 执行；并行叶子仍各自真实运行，不能把这个数量误称为 `2+2p` 个串行网络往返。正常路径有四个有先后依赖的共识阶段，最终 ACK 收集不增加一次上层共识。

各片当前主节点担任 forward。副本对已经完成共识的阶段记录签发摘要投票，forward 收齐三个不同副本对同一记录的签名，再把完整记录和三票证明转发到目标分片。目标片验证来源、批次、参与方、阶段和签名后进入自己的本地共识。阶段证明不替代目标片 PBFT，且不会让所有副本分别发起重复共识。

客户端只接受目标上层两个不同副本的认证、匹配结果。上层已形成 COMMIT 但叶子尚未 FINISH、或只有部分叶子 ACK，都不算完成交易。上层不代替叶子重做应用计算；同一跨片交易在多个叶子执行，客户端 TPS 仍只算一笔。

## 4. 锁、批量和执行

PREPARE 在本地 PBFT 顺序中取得读写 key 的锁，保存实际使用的读集、写入意图和 Fibonacci 计算结果。准备结果尚未成为应用 KV；只有 FINISH 的 COMMIT 经叶子 PBFT 提交后才更新业务状态。同批多笔访问同一 key 时按批内顺序使用逐步更新的暂存状态。

准备期间片内交易也必须尊重锁。FINISH 释放锁之前不能让另一个冲突事务改变准备读取的状态。收到正常重传时复用已保存的记录，不能再次执行同一个已准备事务；收到 ABORT 后的新尝试使用新的批次标识，重新读取已提交状态并计算。

上层最多保留八个未完成业务批次，和共享 Saguaro 调度一致。其访问 key 索引跳过与当前在途批次冲突的请求，允许独立 key 的事务继续选批；索引在收齐叶子最终 ACK 后释放。各片本地 PBFT 仍一次只发起一个新共识批次，远端等待不永久占用这个本地槽位。本版本不加入投机执行或重做流水线。

`cross_shard_batch_size` 限制一个跨片业务批次的交易数，`cross_shard_batch_wait_ms` 控制未凑满时的合批等待；具有相同参与集合的客户端请求可合入一个业务批次。一次 INIT 批量里的交易随后一起走 PREPARE、DECIDE 和 FINISH，并未省去 2PC 阶段。客户端 `--batch` 控制请求内交易数；普通片内共识使用 `batch_size` 和 `batch_wait_ms`。

参与方不能无期限等待另一事务的锁释放；遇到冲突时返回 NO，上层记录 ABORT，所有参与方完成 FINISH 释放锁后再退避重试原请求。AHL 只有一个上层，因此没有不同 NCA 之间的锁争用，但仍保留同一套冲突、失败和重试实现。ABORT 及重试成本计入客户端总延时，不计为成功交易。

## 5. 去重、恢复与工程范围

消息经过公共 Ed25519 认证和运行 ID 校验。阶段证明绑定协调者、实际参与方、原始事务、批次及阶段；重复阶段消息重新发送已记录结果，不创建第二次本地共识。请求 ID 和交易 ID 的去重沿用 Saguaro，共识有效性依据复制状态，不能依赖某副本先收到最终 ACK。

INIT、准备记录、锁、DECIDE 和历史去重信息进入状态摘要与检查点。forward 更换后从复制状态恢复已经确定的决定和待完成阶段，不重新选择相反的决定。公共 TCP 连接复用、精确延时调度、增量状态摘要和检查点同步继续使用现有实现。

`sag_*` 状态字段与 `saguaro_*` 事件名保留，便于共用检查与故障分析；AHL 节点额外报告 `method=ahl`、`ahl_coordinator` 和 `ahl_topology=two-layer`。最终排空应核对业务队列、锁、普通请求和网络队列，同片四个副本的执行数、状态/KV/链摘要应收敛。

本项目的持久历史和恢复消息随有效交易增长，适合有限负载实验。当前不支持在原运行目录直接重启节点，也没有机器断电后的独立磁盘恢复实现。经典 2PC 在决定不可获得时可能阻塞；不能把已准备事务的一次通信超时擅自当作 ABORT。故障支持范围以实际回归记录为准。

## 6. 双拓扑的可比性与报告

对比入口分别接收 Arbor 的 `--config` 和 AHL 的 `--baseline-config`。只生成或加载一份 unsigned workload，两次运行精确复用交易、请求分组、参与叶子、key/value、顺序、速率和随机种子；保存输入哈希，路由差异单独记录。

示例架构的差异如下：

| 项目 | Arbor | AHL |
|---|---|---|
| 叶子 | 1、2、3、4 | 1、2、3、4 |
| 拓扑 | 1/2→5，3/4→6，5/6→7 | 1/2/3/4→7 |
| 总分片数 / 节点进程数 | 7 / 28 | 5 / 20 |
| `[1,2]` 协调者 | 5 | 7 |
| `[1,3]`、`[1,2,3]` 协调者 | 7 | 7 |
| 各片 PBFT、副本数、计算工作 | 共用配置参数 | 同样参数 |

入口要求两配置的叶子 ID、副本数、host、完整共识参数、执行参数、片内延时及 trace 设置相同；允许父关系、中间分片数量和端口不同。双方共同存在的所有分片对都按显式覆盖与默认值解析实际单向延时，再检查是否一致，不能只比较两个 `shard_links` 数组的字面内容。已删除中间分片的独有链路不要求保留。

网络延时由实际发送方和接收方的分片对决定，不自动把 Arbor 树上的多跳延时相加作为 AHL 的直连延时。AHL 新的父子关系可能使用原配置中的直接链路覆盖或默认片间延时，因此报告必须保存两份完整配置及对应拓扑差异。若要调整共同分片之间的网络假设，应在双方配置中作一致修改；单独改 AHL 的共同链路延时会被对比入口拒绝。

两种方法的完整配置指纹可以不同，差异仅在通过上述检查的拓扑和端口部分。报告的 `method_configs` 保存各自的配置、来源路径、输入与快照 SHA256；`comparison_context` 保存经校验的配对分组、各方法指纹、共同叶子、有效延时和拓扑差异。不同拓扑不能只通过放宽原有“配置指纹相等”检查就计算比值，还必须属于同一合法配对并核对共享输入与实际发送业务负载哈希。

此结果回答的是用户要求的“多层 Arbor 与集中两层 2PC 架构”的性能差异。两边分片总量和节点进程数量不同，不能把比值解释成同拓扑、同进程预算下只替换协议的收益。工具依次启动新集群，避免两个方法同时争用同一台机器资源；重复轮次交替运行顺序。

每轮检查客户端全部唯一交易完成、所有节点执行/协调计数符合该方法、四副本状态收敛且队列和锁排空。只有双方都 PASS 且共享负载一致的轮次计算 TPS 比值；某轮失败会让整组比值留空，失败记录和日志保留。TPS 使用从首次提交到全部客户端最终确认的耗时，延时使用首次提交到对应最终确认的耗时，包含重试和远端等待，单位为秒。

## 7. 验证入口

构建与命令详见 [README.md](README.md)。`make test-ahl` 运行 AHL 工具和真实集群回归，`make test` 运行包括既有方法的完整回归。测试结果报告应分别列出拓扑拒绝、共享负载重映射、两方/三方正常完成、去重、阶段 PBFT 证据、forward 故障与状态追赶等实际执行的用例，不以设计描述替代测试证据。
