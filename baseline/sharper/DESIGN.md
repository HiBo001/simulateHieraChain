# SharPer 基线设计

## 论文依据与复现范围

依据项目 `SharPer.pdf`，SIGMOD 2021，Mohammad Javad Amiri、Divyakant Agrawal、Amr El Abbadi，重点为 PDF 第 7–9 页 Byzantine 跨片协议（Algorithm 3）、冲突和恢复（Algorithm 4、§4.4），以及 §4.3 的高负载 `SUPER_PROPOSE` 方案。PDF 第 3 页脚注允许把连续、相同参与集合的跨片交易组成批次。

采用每片四副本、`f=1`、Ed25519 签名、认证且保持连接的 TCP。片内交易复用本片 PBFT；跨片采用 flattened consensus：所有参与片的副本直接交换 ACCEPT、COMMIT，每个参与片各需要三个不同签名。参与方最近公共祖先不发起、不投票、不决定提交。发起片只是其中一个参与片，不具有 2PC 协调者的决策权。

当前版本是论文正常投票路径的有界实现，使用以下明确的调度限制：选择最小参与片发起、每片只保留一个未执行的跨片 slot、各参与片按 ID 升序预约本地序号。它避免正确主节点下的循环等待，并保留论文的全参与片投票门槛；它增加预约等待，限制了论文默认并行路径的并行度。没有宣称完整复现 Algorithm 4 的宽并发撤回，也没有宣称覆盖任意 Byzantine 主节点调度下的全部活性场景。论文 TPS 数值不能直接作为本机实现的性能结论。

## 输入与路由

公共未签名 workload 保持原来的 NCA `target`。SharPer 客户端读取后、签名前将跨片 target 改成最小参与叶子，交易 ID、顺序、参与方、key/value 和读写集不变。这样三个方法能重放同一业务输入，而各自使用实际协议要求的路由。

初次请求只发给 `f+1=2` 个副本；故障重试才扩大到四个副本。副本以交易 ID 和交易摘要去重。已完成的原请求重传返回原结果；换请求 ID 的同交易重放返回 `duplicate`。相同 ID 携带不同内容返回冲突错误。别名请求不会再次共识同一笔未完成交易。

## 正常跨片流程

1. 发起片 primary 选取相同参与集合的签名 CLIENT 请求，按照 `cross_shard_batch_size` 合并。每个请求仍保持原签名和原顺序，不把片内、跨片交易放进同一块。
2. primary 向所有参与片的全部副本发送 `SH_SUPER_PROPOSE`。签名小头绑定批次、发起序号、参与片集合及完整签名请求数组的 SHA256；请求数组作为消息附带数据传输。
3. 参与片 primary 仅在收到所有更小参与片各三个匹配 ACCEPT 后预约自己的下一个本地序号。它用签名 `SH_LOCAL_CLAIM` 绑定本片序号、ballot、批次、请求摘要和原始签名 proposal 摘要，在片内传播 PREPREPARE 格式的赋值。该格式复用序号、日志和恢复框架，不在跨片路径再运行一轮本地 PREPARE/COMMIT。
4. 本片每个副本验证请求、claim、前缀预约证明和本地顺序后，直接向所有参与片的全部副本发送 `SH_ACCEPT`。只有所有参与片各三个不同副本对同一 claim 投票，才能进入下一步。
5. 每个副本发送 `SH_COMMIT`，绑定完整参与片序号向量、claim 向量和本片读取记录。该记录包含批次开始前账户状态以及交易有序写集、重复标志；相同参与片的三个 COMMIT 必须具有相同记录，所有参与片必须具有相同序号和 claim 向量。
6. 收齐每个参与片三个匹配 COMMIT 后形成全局证书。本片等前序本地序号执行完，再校验自己的读取记录与真实状态一致，实际运行 Fibonacci 并写入 KV。证书进入 `commits.jsonl`，执行状态、去重记录和链摘要按本地序号推进。

严格限定跨片 value 为 `requests`、`sharper_propose`、`sharper_claim` 三个字段。请求数组被签名头摘要绑定，签名头被 claim 摘要绑定，完整 claim 被 ACCEPT 和 COMMIT 向量绑定；不能加入未被投票覆盖的业务字段，避免主节点让不同副本执行不同 value。

升序预约不会形成正确主节点下的资源环：每笔事务持有较小的参与片 slot 后才等待更大的参与片，循环等待要求片 ID 严格递增后回到原点，这是不可能的。片内交易只占一个本片 slot，不等待远端。已预约的跨片 slot 不允许后续片内或跨片事务绕过，不做推测执行或流水线。

## 实际执行与完成统计

读取记录由 COMMIT 投票共同认证，没有另设读取协调者。一个批次中的同键交易按请求、交易顺序串行计算。每笔事务读取本片旧账户和其他参与片旧账户；计算方式与 Arbor、Saguaro 的公共实验业务保持一致：

`new_value = access.value + Fibonacci + sum(remote_old.value)`（uint64 溢出语义）。版本加一，摘要包含旧账户、远端账户、完整交易和当前 owner。所有参与片的临时账户在批内逐笔推进；已提交同交易不会再次执行 Fibonacci 或更新账户。

论文客户端接受本片 `f+1` 匹配回复。本项目为与 Arbor、Saguaro 的“所有相关叶子实际执行完成”口径一致，增加只报告执行完成的 `SH_EXECUTED`：发起片收到每个参与片三个匹配执行通知后返回结果，客户端再要求两个不同发起片副本的匹配回复。它不是新的排序或业务提交共识，但会增加通知与等待成本，应在性能分析中说明。

客户端 TPS 为唯一实际执行交易数除以从提交开始到所有请求确认的耗时。平均、p50、p95、p99 延时单位为秒。队列排空和所有副本状态一致检查独立于客户端确认，失败、超时、只排序未执行的轮次不计为有效吞吐。

## 恢复和认证

共享 PBFT 框架提供片内换主、稳定检查点和证书追赶。SharPer 额外把当前本地预约、原始发起消息及已经投出的 COMMIT 放入签名 VIEW_CHANGE，并逐项验证签名、所属分片、原始请求摘要、序号窗口和记录内容。

完整全参与片 prepared / commit 证明优先，不能被单个高 view 的弱预约覆盖；没有完整证明的序号，至少需要两个不同本片 VIEW_CHANGE 提供相同预约，才能恢复。已经发出的 COMMIT 在该运行中保留，不因换主或安装检查点清除。恢复出的 value、claim 和请求保持一致。

消息重传使用固定间隔，早到但尚未登记批次的消息可由重传补偿。新的可执行工作激活本地超时计时，重复请求不刷新超时。正常等待远端票不会旋转健康本地主节点；主节点失联可触发本片换主。执行后发送本片已执行序号的小提示，让落后副本走已有的认证证书/检查点恢复路径。

公开恢复用例覆盖掉线副本、主节点失联、处理中换主、暂时不足 quorum 后恢复、恶意证书及恢复证据。保持心跳但故意分裂预约/扣消息的 Byzantine 主节点活性，需要更完整的事务级故障归因和冲突恢复，当前不作保证。同一运行目录中进程崩溃后的直接重启仍被公共框架禁止，以防丢失投票承诺；需要启动新 run。

当前历史业务状态、去重记录、批次及恢复证据持续保留；检查点证书会回收窗口中的旧 slot，业务去重历史不会随意删除。长期运行的历史归档和内存上限尚未实现，不能把一次有限负载的 TPS 解释为无限时长稳定性能。

## 对比与测试入口

`baseline/compare.py --baseline sharper` 对比固定参与片的 Arbor/SharPer。`baseline/compare_mixed.py --baseline sharper` 自动生成 90% 双片、10% 三片负载，或通过 `--workload` 精确重放原 JSON。二者使用相同配置，顺序运行独立的新集群，重复轮次交替方法顺序。结果保存配置、业务输入 SHA256、二进制 SHA256、客户端结果和全部副本状态，完整成功才计算比值。

参见本目录 README 的完整指令。`make test-sharper` 运行工具测试、认证恢复单元测试和真实集群回归；`make test` 同时回归 Arbor、Saguaro、SharPer。
